# Calma target ICP + hardening loop (2026-07-03)

## The ICP (who we make flawless first)

**Primary ICP — the classical-ML "model-comparison" author.** A practitioner or researcher who publishes a
computational result alongside runnable code in a public repo:

- **Stack:** Python, CPU-runnable — scikit-learn / pandas / numpy / xgboost / lightgbm. No GPU, no giant data.
- **Data:** a committed dataset (CSV) OR a library built-in (sklearn `load_*`, seaborn) OR a small download.
- **Entry:** a runnable `*.py` eval/train script, or a notebook, that computes the reported metric(s).
- **The reported number:** a README leaderboard table (Model × accuracy/F1/…), a committed `results.json`/
  `results.csv`, or a printed metric. Often a *comparison* of several models/datasets.
- **Job to be done:** "Is my reported number real — not leaked, not a trivial baseline, not a misreport —
  and does it reproduce?"

**Why this segment first:** highest density of committed-artifact + runnable-eval, lowest infra friction, and
exactly where the shipped work bites — artifact ingestion (leaderboard tables → per-cell claims), the
reverse map (run the script that wrote the table), and the no-run validity checks (leakage / trivial /
misreport). Adjacent segments (paper-reproduction, quant backtests, agentic CI) are the same engine with
more infra; we earn them after this one is flawless.

## "Flawless for the ICP" = the exit bar

On a curated corpus of real ICP repos:
- **False-confirm rate = 0** (inviolable — never confirm a wrong number).
- **Reproduction ≥ 0.8** of CPU-runnable repos actually run (env synthesis / entry detection good enough).
- **Binding ≥ 0.8** of discovered headline claims bind (or fail-closed to INCONCLUSIVE, never wrong).
- **Validity checks fire** where leakage / trivial-baseline / misreport are present, and stay silent where
  they aren't (no false-refute, no false-invalidate).
- **No crashes / no hangs** — every repo returns a verdict or an honest DISCOVERED, within budget.

## The loop

Curate a batch of real ICP repos → run the product (run_spike / validity_scan) → read the logs → for each
failure, classify (repro gap / binding gap / validity gap / crash / false-verdict) → fix the highest-leverage
one → re-run → repeat until the exit bar holds. Each cycle logged below.
